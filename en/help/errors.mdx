When a MaxAPI request fails, inspect the HTTP status first, then the response's error details. Models and upstream services can return different error structures, so avoid relying on one exact error string.

## Locate the failing layer

| Observation | Start with | Next action |
| --- | --- | --- |
| Missing environment variable or module | Application startup and dependencies | Check that the process loads the key and uses the environment where the package is installed |
| Connection fails without an HTTP status | Network, DNS, proxy or TLS | Request the model list from the same environment as the application |
| Non-2xx HTTP response | Authentication, request, access or server processing | Retain status and error body, then use the table below |
| HTTP success but JSON parsing fails | Response reader | Check for SSE, plain text, audio or an HTML page |
| HTTP success but a task is queued | Task lifecycle | Save the task ID and query it; submission is not completion |
| Valid text with an unsuitable answer | Model input and application validation | Check history, instructions, finish reason and result validation |

If cURL works and the SDK does not, compare the final URL, model ID, actual fields and runtime environment. An SDK exception describes what the client observed; its class name is not necessarily a platform business error code.

## Preserve one diagnostic response

This model-list request saves response headers and body separately and prints the HTTP status. The 10-second connection and 30-second total timeouts are diagnostic choices, not MaxAPI service limits.

```bash Save diagnostic files
curl --silent --show-error \
  --connect-timeout 10 \
  --max-time 30 \
  --dump-header diagnostic-headers.txt \
  --output diagnostic-body.txt \
  --write-out 'HTTP %{http_code}\n' \
  https://api.maxapi.ai/v1/models \
  -H "Authorization: Bearer $MAXAPI_API_KEY"
```

- When a real HTTP status is available, inspect `diagnostic-body.txt`; it need not be JSON.
- `HTTP 000` with a cURL connection error means there was no usable HTTP response. Diagnose networking first.
- This command omits `--fail`, so an HTTP `401` can still have a successful process exit code. Use the printed HTTP status.
- Inspect files for account information, personal data and sensitive inputs before sharing. Avoid collecting public diagnostic material with logging that exposes authentication headers.

## Capture a failed API response

Even if model listing succeeds, retain the response from the endpoint that actually fails. This example reuses `request.json` from the [quickstart](/en/quickstart) to resend the Chat Completions request and save headers and body separately. Confirm the file exists in your current directory and `MAXAPI_API_KEY` is set in your terminal.

```bash Save the chat response
: "${MAXAPI_API_KEY:?Set MAXAPI_API_KEY first}"
curl --silent --show-error \
  --connect-timeout 10 \
  --max-time 60 \
  --dump-header failed-response-headers.txt \
  --output failed-response-body.txt \
  --write-out 'HTTP %{http_code}\n' \
  https://api.maxapi.ai/v1/chat/completions \
  -H "Authorization: Bearer $MAXAPI_API_KEY" \
  -H "Content-Type: application/json" \
  --data-binary @request.json
diagnostic_exit=$?
printf 'cURL exit %s\n' "$diagnostic_exit"
```

This submits a new generation request and may incur usage. If the previous attempt only timed out and its outcome is unknown, check existing tasks or console records first. The 60-second client timeout is an example you can adjust for diagnosis.

1. Record the HTTP status and `cURL exit`. This command omits `--fail`, so an exit code of `0` still requires checking the HTTP status. Resolve cURL errors when the exit code is nonzero; a timeout or interrupted connection can leave a partial body even after HTTP `200` arrives.
2. Inspect `failed-response-headers.txt` for the response `Content-Type` and any request identifier actually returned.
3. Keep the original error body in `failed-response-body.txt`. JSON errors may contain `error.message`, `error.type` or `error.code`; retain the actual structure when these fields are absent instead of saving only an SDK exception name.
4. Make a redacted copy before sharing. Remove sensitive inputs, account information and personal data. Do not include API keys or full authorization headers.

`--data-binary @request.json` reads the file's original contents. Do not change the model or parameters just to capture a response. If the original request uses `stream: true`, the saved body may be SSE; read it using the [streaming format](/en/guides/streaming), not as one JSON object. Use the corresponding URL and request file for other JSON endpoints. For multipart uploads, preserve the file fields described below.

## Interpret HTTP status codes

This table gives general HTTP troubleshooting directions, not a complete MaxAPI error specification. Use the actual response to identify the cause.

| Status | Common direction | Action |
| --- | --- | --- |
| `400` | Invalid body, field type or model parameter | Check JSON and add options back to a minimal request one at a time |
| `401` | Missing or invalid key or authorization header | Check environment variables, Bearer formatting and key validity |
| `403` | Insufficient access | Verify account and model access conditions |
| `404` | Route or resource not found | Check the base URL, endpoint and model ID |
| `429` | Frequency, quota or usage restrictions | Read details, check account state, reduce concurrency and retry with backoff where appropriate |
| `5xx` | Service or upstream failure | Retain the response, retry a bounded number of times and investigate persistent failures |

## Start with a minimal request

Check connectivity and authentication with the model list:

```bash List models
curl --fail-with-body https://api.maxapi.ai/v1/models \
  -H "Authorization: Bearer $MAXAPI_API_KEY"
```

Then follow the [quickstart](/en/quickstart) with only `model` and `messages`. If that succeeds, restore optional parameters, larger inputs and streaming one at a time.

## Check the final URL

| Use | Correct address |
| --- | --- |
| Compatible SDK base URL | `https://api.maxapi.ai/v1` |
| Direct HTTP chat | `https://api.maxapi.ai/v1/chat/completions` |
| Direct HTTP model list | `https://api.maxapi.ai/v1/models` |

Avoid a duplicate `/v1` and do not send API requests to the website or console domain.

## Diagnose timeouts and connection failures

If no HTTP response arrives, check network access, DNS, proxy settings and your server's access to the API domain. Long generations may need an application-appropriate timeout.

For streaming, check whether an intermediate service buffers output or closes connections early. See [streaming](/en/guides/streaming).

## Use bounded retries

Network interruptions and some `429` or `5xx` errors may be retryable. Invalid keys, wrong model IDs and unsupported parameters generally need correction first.

Increase the delay between attempts, add random jitter and set a maximum number of attempts. Respect `Retry-After` when provided and applicable. Check the SDK's existing retries before adding another loop.

A timeout does not prove that the server performed no work. Retrying may generate duplicate output or additional usage.

## Collect useful diagnostics

When contacting support through your [console](https://platform.maxapi.ai), include the time and time zone, route, model ID, HTTP status, redacted response and request identifier if one was returned.

Remove API keys, personal data and sensitive business content. Never share a complete `Authorization` header.

## HTTP 200 with no generated output

Task APIs can return a business `code`, `status` or error object inside a successful HTTP response:

- Midjourney's submission `result` is a task ID, not a completed image.
- Suno v2 generation status does not replace checking each item in `clips`.
- A queued or processing video requires a matching task query.
- Native protocols may use `base_resp` or other error fields instead of `choices`.

Follow [asynchronous tasks](/en/guides/async-tasks).

## Task queries return 404 or never finish

Match the query protocol to the source of the ID. Do not mix `clips[].id`, `operation.name` and `data.task_id`, or reuse a fixed example ID. Retain unknown states and set an overall deadline. After a task fails, inspect inputs, permissions and the error instead of submitting new tasks to check progress.

## Upload or download format errors

Distinguish the endpoint's input format from its result download format. The same image may need different encoding for different endpoints.

| Scenario | Correct handling | Check first |
| --- | --- | --- |
| Multipart endpoints such as audio transcription and translation | Send the actual file with cURL `-F 'file=@audio.mp3'` or an SDK file parameter; let the client generate the `multipart/form-data` boundary | The file exists in the application environment; no manually set `application/json` or Content-Type missing a boundary. See [transcription](/en/api-reference/audio-transcriptions) |
| Midjourney Imagine reference images, Blend and Describe | Send image Data URIs such as `data:image/png;base64,...` in JSON; Imagine / Blend use `base64Array`, while Describe uses one `base64` value | Encode image bytes with the correct MIME type; do not place a path, URL or `@filename` in a Base64 field. See [Midjourney inputs](/en/media/midjourney/inputs) |
| Remote image URLs for vision | Put an accessible direct image link in `image_url.url`; the request body remains JSON | The processing service can access the URL without your browser login; it returns an image, not HTML. A local path is not a remote URL. See [vision](/en/guides/vision) |
| Speech generation or result downloads | Confirm HTTP success and the expected `Content-Type`, then save the response as bytes | Do not save error JSON or HTML as audio or images; do not attach the MaxAPI key when downloading from a third-party result URL. See [speech](/en/api-reference/audio-speech) and [asynchronous tasks](/en/guides/async-tasks) |

JSON Data URIs, remote URLs and multipart file fields are not interchangeable. Use the field names and input formats documented for the endpoint.

## Narrow the failure by request type

<Tabs>
<Tab title="Chat and streaming">

Begin with one short user message, no streaming and only `model` and `messages`. Enable `stream` after that works. If raw events arrive but the page does not update, inspect application buffering. If the connection closes early, compare timeouts in the client, gateway and application.

Check tool calls when `content` is empty and `finish_reason` when output is truncated. An empty SDK property does not by itself establish that the whole request failed.

</Tab>
<Tab title="Images and files">

Start with a small image or short recording you can open locally. Choose multipart, a Data URI or a remote URL using the [format comparison](#upload-or-download-format-errors). For uploads, check that the file exists in the application environment. For Base64, check the prefix and complete encoded data. For URLs, check login requirements, expiry and access restrictions.

If the small file works, compare the original file's actual encoding, dimensions or duration with the model requirements. Renaming an extension does not convert encoding.

</Tab>
<Tab title="Video and music tasks">

Separate submission, status queries and result downloads. Save the ID after submission instead of submitting again to check progress. If querying fails, verify the ID's source and protocol. If downloading fails, retry the existing result URL before generating again.

Reaching your application deadline leaves the result unresolved; it does not prove generation failed. Query again later where supported. See [asynchronous tasks](/en/guides/async-tasks) for protocol fields.

</Tab>
</Tabs>

## Prepare a support request

Use the smallest reproducible input without a real key. Fill in this template. Include a request identifier only when the API actually returns one; do not invent its header name.

```text Support request template
Time and time zone: YYYY-MM-DD HH:mm:ss with time zone
Environment: local / cloud; language and SDK version
Method and path: POST /v1/chat/completions
Model ID: actual model ID
HTTP status: actual status, or no response
Request or task identifier: if returned
Frequency: every request / intermittent; last successful time
Minimal reproduction: required fields and shareable input only
Expected result:
Actual result: redacted error or status
Checks performed: whether model listing and minimal requests succeed
```

After redacting the details, submit them through the support entry in your [console](https://platform.maxapi.ai). If a key entered public code, screenshots or logs, handle that key in the console before sharing a sanitized reproduction.
