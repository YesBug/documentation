Video, music and some image requests can take time to complete. A successful submission usually means a task was accepted. Your application must query its status until it succeeds or fails.

## Follow a task through its lifecycle

1. Submit using the selected protocol and record the protocol family, model and submission time.
2. Save the returned task ID, song clip ID or operation name.
3. Poll the matching query endpoint, or receive a supported callback.
4. Confirm the terminal state. Read output on success or retain error details on failure.
5. Retrieve and persist the generated asset according to your application's needs.

Associate the task ID with a business record. Refreshing a page should not submit another generation request.

## Persist enough information to resume

Keep the following application records so a refresh, restart or missed callback does not lose the task. These are your application's fields, not extra parameters to send to MaxAPI.

| Application record | Purpose |
| --- | --- |
| Business record ID and owner | Locate the request and authorize access to its result |
| Protocol, submission path and model | Select the matching query route and parser |
| Task IDs, clip IDs or operation name | Resume queries; one generation can produce several result IDs |
| Submission time, last query time and raw state | Show progress and identify tasks that stopped updating |
| Latest response and failure reason | Diagnose format differences; redact keys and unnecessary sensitive input before storing |
| Result URL in your own storage | Preserve an asset independently of temporary generation URLs |

Return your business record ID to the frontend. Repeatedly opening the result view should read that record. Only an explicit new generation action should submit another API task.

## Keep protocol identifiers distinct

| Protocol | Identifier from submission | Query |
| --- | --- | --- |
| Unified video | `task_id` | `GET /v2/videos/generations/{task_id}` |
| Midjourney | `result` | `GET /mj/task/{id}/fetch` |
| Suno NewAPI-compatible | `data.task_id` | `GET /suno/fetch/{task_id}` |
| Suno v2 | `clips[].id`, possibly several | `GET /suno/v2/feed?ids=...` |
| Native Hailuo-compatible | `task_id` | `GET /hailuo/v1/query/video_generation?task_id=...` |
| Veo long-running operation | Operation `name` | POST `operationName` to the matching `fetchPredictOperation` route |

Check the actual response for your channel. Do not pass one protocol's ID to another protocol's endpoint.

## Map states per protocol

Your application can normalize states, but the original values differ:

| Application state | Values seen across reference examples | Action |
| --- | --- | --- |
| Waiting | `NOT_START`, `QUEUED`, `PENDING` | Retain the task and query later |
| Processing | `IN_PROGRESS`, `RUNNING`, `processing` | Continue waiting |
| Succeeded | `SUCCESS`, `SUCCEEDED`, `completed`, `complete` | Read the protocol's result fields |
| Failed | `FAILURE`, `FAILED`, `failed`, `error` | Stop polling and record the error |

These are cross-protocol examples, not an exhaustive enum for any endpoint. Preserve unknown values and investigate within a bounded waiting period. A state that is not explicitly failure is not necessarily success.

## Run a complete Midjourney poller

This script accepts an existing Midjourney task ID, exits on success or failure, and saves the latest response to `mj-task.json`. It creates no new generation task, so you can resume after restarting your application. First submit a task using the [Midjourney guide](/en/media/midjourney) and retain `TASK_ID`.

```bash Install the dependency
python -m pip install requests
```

```python wait_for_midjourney.py
import json
import os
import sys
import time
from pathlib import Path
from urllib.parse import quote

import requests


def wait_for_midjourney(task_id, timeout_seconds=600, interval_seconds=5):
    url = f"https://api.maxapi.ai/mj/task/{quote(task_id, safe='')}/fetch"
    headers = {"Authorization": f"Bearer {os.environ['MAXAPI_API_KEY']}"}
    deadline = time.monotonic() + timeout_seconds
    pending = {"NOT_START", "SUBMITTED", "IN_PROGRESS"}

    while time.monotonic() < deadline:
        response = requests.get(url, headers=headers, timeout=(10, 30))
        response.raise_for_status()
        task = response.json()
        Path("mj-task.json").write_text(
            json.dumps(task, ensure_ascii=False, indent=2), encoding="utf-8"
        )
        status = task.get("status")
        print(f"{task_id}: {status}, {task.get('progress', '')}", file=sys.stderr)
        if status == "SUCCESS":
            if not task.get("imageUrl"):
                raise RuntimeError("Task succeeded but imageUrl is missing; inspect mj-task.json")
            return task
        if status == "FAILURE":
            raise RuntimeError(task.get("failReason") or "Midjourney generation failed")
        if status not in pending:
            raise RuntimeError(f"Unrecognized task state: {status!r}; inspect mj-task.json")
        remaining = deadline - time.monotonic()
        if remaining > 0:
            time.sleep(min(interval_seconds, remaining))
    raise TimeoutError(f"Still waiting for {task_id}; query the same ID again later")


if __name__ == "__main__":
    if len(sys.argv) != 2:
        raise SystemExit("Usage: python wait_for_midjourney.py TASK_ID")
    wait_for_midjourney(sys.argv[1])
    print("Task complete. Response saved to mj-task.json.")
```

```bash Wait for the submitted task
python wait_for_midjourney.py "$TASK_ID"
```

The 5-second interval and 600-second waiting period are application example values, not MaxAPI rate limits or completion guarantees. Individual HTTP requests have separate connection and read timeouts; an in-flight request can finish after the polling deadline.

| Outcome | Next step |
| --- | --- |
| Success saved to `mj-task.json` | Read `imageUrl` and use the [download example](/en/media/midjourney) |
| Task state `FAILURE` | Inspect `failReason` before deciding whether to change the input and submit again |
| Local waiting timeout | Retain the task ID and rerun later with the same ID |
| HTTP or network error | The script exits; resolve [authentication, rate limit or network errors](/en/help/errors), then query the original ID |
| Unexpected state | Inspect the saved response and route instead of applying a different protocol's parser |

### Move polling to a background worker

Closing a page should not end the business task. Schedule queries on your application backend: query once per worker execution, save the next query time, and release the worker. Stagger queries when managing many tasks.

Record query failures separately from generation failures. Retry temporary query errors after a delay; stop polling once generation explicitly fails. For HTTP `429`, honor a supplied `Retry-After` within your own waiting budget. Retrying a query must not automatically submit another generation.


## Handle submission timeouts

A timed-out request may still have created a task. Retrying blindly can create duplicate work and usage. Query using an ID you received or inspect console records first. Only send an idempotency field when the endpoint explicitly supports it; do not assume universal `Idempotency-Key` support.

## Receive callbacks

Some protocols provide `notifyHook`, `notify_hook` or `callback_url`. Their field names and event bodies are not interchangeable.

- Use a reachable HTTPS receiver and acknowledge quickly, moving slow processing into the background.
- Match the task ID to your record and make repeated notifications update the same task.
- Verify the protocol's documented signature mechanism when one is provided; do not invent a signature header.
- If no signature mechanism is specified, query the task endpoint to verify important completion claims.
- Keep polling available to recover from missing, delayed or out-of-order callbacks.

Callbacks originate from a server. `localhost` and private-network-only URLs generally cannot receive them.

### Handle callbacks racing with queries

Locate the record by task ID and apply an atomic state update. After success has been verified and its asset stored, an older processing notification should not move the task backward. Reuse the stored asset when the same completion notification arrives again.

If a notification claims completion but a query does not confirm it, retain the notification for diagnosis and continue scheduling from the query result. A callback processing failure is not a generation failure and should not automatically trigger a new submission.

## Retrieve and retain results

Output URLs may be temporary signed URLs. There is no universal retention duration documented here. Confirm success, media type and file size before downloading, then store required assets yourself. If a link expires, query the task again for its current result URL.

Preserve the original ID so users can leave your page and return to check the same task later.
